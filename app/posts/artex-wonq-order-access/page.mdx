원큐오더에서 확인하고 싶었던 것은 서버에 접속할 수 있는지보다 **내 주문을 볼 수 있는 경로로 다른 사람의 주문까지 볼 수 있는지**였습니다. 주문 화면과 가맹점 화면이 정상 동작해도, API가 요청자의 권한을 검사하지 않으면 화면 밖에서 데이터를 읽을 수 있기 때문입니다.

실험 결과, 생성한 두 주문은 **다른 점주 계정뿐 아니라 인증 헤더가 없는 요청에도 동일한 상세 정보가 반환**됐습니다. 반면 가맹점 테이블 목록은 각 계정의 주문만 반환했습니다. 같은 주문 데이터라도 어떤 API를 거치는지에 따라 접근 경계가 달랐습니다.

이번에는 Windows 노트북에 배포한 테스트 서버에 MacBook의 ARTEX로 실제 요청을 보냈습니다. 앞선 [ARTEX 기본 사용 실습](/posts/artex-ollama-first-use/)이 주어진 응답을 분석하는 연습이었다면, 이번에는 데이터 준비와 HTTP 요청, 결과 비교까지 수행하는 점검입니다.

## 금융권 사고에서 가져온 질문

2026년 10월 14일 금융당국 발표를 전한 [연합뉴스 보도](https://www.yna.co.kr/view/AKR20261014134852002)에서는 침해사고가 확인된 금융회사가 16곳이며, 점검 과정에서 외부 시스템의 인증·인가 누락 등이 지적됐다고 전했습니다. 이 보도를 보고 제가 만든 주문·결제 서비스에도 접근통제에서 빠진 경로가 있는지 확인하기로 했습니다. 개별 금융회사 사고의 공격 방법을 그대로 재현하는 실험은 아닙니다.

구체적인 점검 기준은 [개인정보보호위원회의 API 보안 안내](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=&nttId=12241)에서 가져왔습니다. 로그인 여부를 확인하는 것과 해당 데이터를 조회할 권한을 확인하는 것은 다르며, 서버에서 각 요청의 권한을 검사해야 한다는 내용입니다.

원큐오더에 대입하면 질문은 두 가지가 됩니다. 첫째, 로그인하지 않은 요청이 주문 상세를 읽을 수 있을까요? 둘째, 점주 A의 로그인 정보로 점주 B의 주문을 읽을 수 있을까요? 이를 확인하려면 서로 구분되는 계정과 주문이 필요합니다. 데이터가 없는 상태에서 빈 목록을 한 번 조회하는 것으로는 이 질문에 답할 수 없습니다.

## 테스트 환경과 데이터의 경계

MacBook에서는 ARTEX와 Codex CLI 브리지를 실행했습니다. 이번 작업에 로컬 Ollama 모델은 사용하지 않았습니다. Windows 노트북에는 원큐오더의 프런트엔드와 API를 배포했고, 실제 요청 대상은 동일한 로컬 네트워크의 `192.168.0.20`으로 한정했습니다.

| 구성 | 포트 | 이번 점검에서의 역할 |
| --- | --- | --- |
| 주문 화면 | 3000 | 웹 접근 확인 |
| 가맹점 화면 | 3001 | 웹 접근 확인 |
| PG 관리 화면 | 3002 | 구성 파악, 주문 조회 실험에서는 제외 |
| 주문·회원·가맹점 API | 18080 | 회원가입, 더미 데이터 준비, 조회 비교 |
| PG·모의 카드사·앱카드·모의 은행 | 8081·8082·8083·9090 | 결제·인증 처리 호출 제외 |
| MySQL | 3037 | 직접 접속 및 수정 제외 |

이 표는 테스트 환경에서 전달받은 서비스 구성을 정리한 것이며, 모든 포트의 기능을 검증했다는 의미는 아닙니다. 이번 점검은 주문 API의 데이터 접근에 집중했습니다.

실제 고객·카드·계좌는 사용하지 않습니다. 계정 이름에는 `artex_` 접두어를 붙이고, 이메일은 `example.invalid`, 연락처와 계좌 정보는 사용할 수 없는 테스트 값으로 구성했습니다. 메뉴도 `ARTEX_DUMMY_A`, `ARTEX_DUMMY_B`로 구분하도록 준비했습니다.

## 먼저 API 위치와 인증 거절을 확인했습니다

처음에는 웹 화면의 포트에 API 경로를 요청했습니다. `3000`과 `3001`에서는 HTML 형식의 `404`가 반환됐습니다. 이는 인증이 잘 동작한다는 증거가 아니라 해당 위치에서 API를 찾지 못했다는 결과입니다. 이후 실제 백엔드 포트인 `18080`으로 대상을 바로잡았습니다.

ARTEX의 별도 작업에서 인증 헤더 없이 다음 요청을 보냈습니다.

| 요청 | HTTP 상태 | 해석 |
| --- | --- | --- |
| `GET /api/v1/merchant/info` | 401 | 이 비인증 요청은 거절됨 |
| `GET /api/v1/orders/daily?date=2026-10-20&page=0&size=1` | 401 | 이 비인증 요청은 거절됨 |
| `GET /actuator` | 200 | 공개된 인덱스에서 self·health·health-path 링크 이름 확인 |
| `GET /health` | 500 | 서버 오류 응답, 원인은 별도 확인 필요 |
| 존재하지 않는 비교 경로 | 401 | 기본 인증 정책도 같은 상태를 반환함 |

## 더미 주문을 만드는 경로를 먼저 읽었습니다

데이터를 생성하기 전에 로컬 API 소스를 읽었습니다. 회원가입은 회원과 가맹점을 저장하고, 테이블·메뉴 등록은 로그인한 회원의 가맹점에 데이터를 연결합니다. 이미지 업로드와 QR 생성은 외부 저장소를 사용하므로 실험에서 제외했습니다.

주문 생성 경로도 구분했습니다. 이번에 선택한 `POST /api/v1/orders/prepare`는 소스에서 주문을 `ORDERED`, 결제를 `PENDING` 상태로 저장합니다. PG에 결제 확인을 요청하는 `/verify`나 환불 API를 호출하지 않고도 조회할 주문을 준비할 수 있는 경로입니다.

준비한 순서는 다음과 같습니다.

1. 테스트 점주 A를 가입시키고 정상 로그인합니다.
2. A의 가맹점에 테이블 하나와 100원짜리 더미 메뉴 하나를 만듭니다.
3. A의 메뉴를 담은 결제 대기 주문 하나를 생성합니다.
4. 테스트 점주 B에도 같은 과정을 수행하되 메뉴 가격은 200원으로 구분합니다.
5. 생성 응답에서 받은 주문 코드만 사용해 접근 권한을 비교합니다.

테이블 번호는 A가 `902`, B가 `903`입니다. 소스의 주문 준비 로직은 요청의 `tableId`를 DB의 테이블 PK가 아니라 가맹점 내부의 테이블 번호로 조회하고 있어, 이 규칙에 맞춰 준비했습니다. 생성 응답의 PK와 테이블 번호는 별도로 기록하도록 했습니다.

## ARTEX에 작업을 등록한 방법

ARTEX의 **작업 → 새 작업**에서 이름을 `더미 주문 A/B — 비인증·교차 계정 조회 검증`으로 입력했습니다. 설명에는 대상뿐 아니라 데이터 생성 허용 범위와 금지할 동작을 함께 적었습니다. 목표에는 ‘서버를 장악하라’ 대신 ‘같은 주문을 요청자의 신원만 바꿔 조회하고 결과를 비교하라’를 넣었습니다.

실제 입력한 설명의 핵심은 다음과 같습니다.

```text
대상: 소유자가 통제하는 192.168.0.20:18080
생성: 더미 계정 A/B와 각각의 테이블·메뉴·결제 대기 주문 1개
검증: 본인, 상대 계정, 인증 헤더 없는 상태의 주문 상세 조회
대조군: 각 계정의 자기 매장 테이블 목록
제한: Worker 하나, 최대 18회, 요청 간격 1초, 요청당 5초 제한
금지: 실제 결제, 환불, DB 직접 접속, 삭제, 다른 호스트 탐색
증거: 상태 코드와 생성한 주문·메뉴의 반환 여부
비밀정보: 비밀번호와 토큰은 출력하지 않음
```

작업별 허용 규칙에는 IP 완전 일치로 `192.168.0.20`을 추가했습니다. 고급 설정에서는 작업 시간 제한을 10분으로 두고, 첫 의도 직접 전달을 켰으며, 자산 커버리지 기능은 껐습니다. 범위를 넓혀 탐색하기보다 정해진 비교 실험 하나를 수행하도록 구성한 것입니다.

이번에는 요청 순서와 비밀정보 처리를 고정하려고 검증 스크립트를 먼저 작성하고, ARTEX Worker가 이를 읽고 한 번 실행하도록 했습니다. **ARTEX가 처음부터 취약점과 공격 코드를 스스로 찾아낸 실험은 아닙니다.** 사람이 설계한 권한 비교를 ARTEX에서 실행하고, 도구 출력과 판단 과정을 추적한 실험입니다.

스크립트는 계정 비밀번호를 실행 시 무작위로 만들고 로그인 토큰을 메모리에만 보관합니다. 증거 파일에는 요청 시각, 메서드, 경로, 응답 상태, 본문 길이와 SHA-256, 더미 데이터 일치 여부를 남기도록 했습니다. 실패하면 그 단계에서 멈추고 이미 생성된 데이터의 식별자를 보존합니다.

## 실제로 생성한 데이터와 조회 결과

2026년 10월 20일 00:27~00:28 KST에 ARTEX 작업 `#6`의 Worker `#23`이 스크립트를 실행했습니다. 준비 요청 10회와 조회 요청 8회, 총 18회가 실행됐고 모두 HTTP `200`을 반환했습니다. 다음 값은 예시로 만든 숫자가 아니라 생성 응답에서 기록한 식별자입니다.

| 항목 | 점주 A | 점주 B |
| --- | --- | --- |
| 회원 ID / 가맹점 ID | 2 / 2 | 3 / 3 |
| 테이블 PK / 번호 | 2 / 902 | 3 / 903 |
| 메뉴 ID | 2 | 3 |
| 주문 코드 | `261020T002752_t902` | `261020T002758_t903` |
| 금액 | 100원 | 200원 |
| 주문 / 결제 상태 | ORDERED / PENDING | ORDERED / PENDING |

조회는 `GET /api/v1/orders/code/{orderCode}`로 수행했습니다. 주문 코드를 하나 고정하고 Authorization 헤더만 바꿨습니다. 본인 토큰, 상대 계정의 토큰, 헤더가 없는 경우를 각각 한 번씩 비교했습니다.

| 조회 대상 | 요청자 | HTTP | 해당 주문 반환 | 해당 더미 메뉴 반환 |
| --- | --- | --- | --- | --- |
| A 주문 | A | 200 | 확인 | 확인 |
| A 주문 | B | 200 | 확인 | 확인 |
| A 주문 | 비인증 | 200 | 확인 | 확인 |
| B 주문 | B | 200 | 확인 | 확인 |
| B 주문 | A | 200 | 확인 | 확인 |
| B 주문 | 비인증 | 200 | 확인 | 확인 |

상태 코드만 같았던 것이 아닙니다. 각 주문의 세 응답은 모두 414바이트였고, 같은 주문끼리는 응답 본문의 SHA-256도 일치했습니다. A 주문은 `7c9db1d740ce…`, B 주문은 `264bb4ceb558…`로 기록됐습니다. 로그인 주체를 바꿔도 동일한 응답을 받았다는 비교 근거입니다.

응답에는 주문 코드, 테이블 번호, 금액, 주문 상태, 결제 상태, 결제 수단, 결제 완료 시각 필드, 생성 시각, 메뉴 목록이 포함됐습니다. 생성한 주문은 결제 대기 상태였고, 이 실험에서 결제 승인이나 환불을 실행하지 않았습니다.

위 화면의 `knownOrderReturned`는 응답 주문 코드가 생성한 주문 코드와 일치하는지, `ownDummyMenuReturned`는 조회 대상 주문의 더미 메뉴 ID가 응답에 포함되는지 검사한 값입니다. 후자의 `own`은 요청자의 소유권이 아니라 **해당 테스트 주문의 메뉴와 일치한다**는 뜻입니다.

대조군으로 각 계정에서 `GET /api/v1/merchant/tables`도 요청했습니다. A의 응답에는 A 주문 코드만, B의 응답에는 B 주문 코드만 있었습니다. 상대 주문 코드는 없었습니다. 따라서 ‘계정이 구분되지 않는다’는 설명보다는 **가맹점 목록 경로는 계정을 구분하지만 주문 코드 조회 경로는 요청자의 계정과 무관하게 응답한다**는 설명이 이번 결과에 맞습니다.

## 주문 코드만으로 조회되는 이유

로컬에서 검토한 API 소스의 기준 커밋은 `85ebd90c49d3773d1f2bcdac54a0106702134a8f`입니다. 아래 코드는 이 체크아웃의 발췌이며, Windows 배포 바이너리의 커밋까지 대조한 것은 아닙니다. 실제 배포 동작은 앞의 HTTP 결과로 별도 확인했습니다.

[`WebSecurityConfig.java`](https://github.com/WON-Q/api-server/blob/85ebd90c49d3773d1f2bcdac54a0106702134a8f/src/main/java/com/fisa/wonq/global/security/config/WebSecurityConfig.java)는 다음 경로를 인증 없이 허용하는 목록에 넣고 있습니다.

```java
antMatcher("/api/v1/orders/code/{orderCode}")
```

[`OrderController.java`](https://github.com/WON-Q/api-server/blob/85ebd90c49d3773d1f2bcdac54a0106702134a8f/src/main/java/com/fisa/wonq/order/controller/OrderController.java)의 조회 메서드는 주문 코드만 받아 서비스에 전달합니다. 로그인 회원 정보는 매개변수로 받지 않습니다.

```java
OrderDetailResponse dto = orderService.getOrderByCode(orderCode);
```

[`OrderService.java`](https://github.com/WON-Q/api-server/blob/85ebd90c49d3773d1f2bcdac54a0106702134a8f/src/main/java/com/fisa/wonq/order/service/OrderService.java)도 주문 코드로 데이터를 찾고 DTO를 반환합니다.

```java
Order order = orderRepo
        .findWithDetailsByOrderCode(orderCode)
        .orElseThrow(() -> new IllegalArgumentException("Invalid orderCode: " + orderCode));
return toDto(order);
```

원큐오더는 비회원이 QR로 주문하는 서비스이므로, 비회원 조회 경로 자체가 곧 잘못된 기능은 아닙니다. 문제는 비회원 주문자를 무엇으로 구분하느냐입니다. 이번 요청에는 주문 코드 이외의 영수증 접근 토큰이나 주문자 세션 증명이 없었지만 상세가 반환됐습니다. 사실상 주문 코드가 조회 권한을 대신하고 있습니다.

그런데 이 소스의 코드는 생성 시각과 테이블 번호로 구성됩니다.

```java
String orderCode = LocalDateTime.now()
        .format(DateTimeFormatter.ofPattern("yyMMdd'T'HHmmss"))
        + "_t" + table.getTableNumber();
```

이 값은 주문을 사람이 구분하기에는 편하지만 비밀 접근키로 설계된 난수는 아닙니다. **비회원 조회를 유지하더라도, 표시용 주문 번호를 아는 것만으로 상세를 읽게 하는 구조는 보완이 필요합니다.** 이번에는 직접 생성해 알고 있는 두 코드만 사용했습니다. 알 수 없는 주문 코드를 추측하거나 대량으로 찾는 실험은 하지 않았습니다.

## ARTEX가 무서운 지점은 무엇일까요

이번 결과는 서버의 관리자 권한을 빼앗거나 DB에 직접 들어가 얻은 것이 아닙니다. 정상적인 HTTP 요청의 경로와 인증 헤더를 바꿨고, 서버가 주문 정보를 돌려줬습니다. 서버 침입에 성공해야만 데이터가 노출되는 것은 아니라는 점이 중요했습니다.

ARTEX에서는 작업 설명을 바탕으로 제약과 목표를 정리하고, Worker가 도구를 실행하고, 결과를 사실로 기록하는 과정이 한 작업에 연결됐습니다. 이번 Worker는 스크립트를 읽고 실행한 뒤 조회 결과를 사실 `#25`로 남겼습니다. 다음 화면은 그 실행 기록입니다.

제가 얻은 교훈은 ‘AI가 있으니 모든 서버가 뚫린다’가 아니었습니다. **서버가 빠뜨린 권한 검사를 요청 도구가 대신 지켜주지는 않는다**는 점입니다. 방어자에게도 같은 도구가 유용합니다. 실패를 기대하는 요청을 구체적으로 설계하고 결과를 대조하면, 정상 화면만 확인할 때 지나치기 쉬운 경계를 점검할 수 있습니다.

## 수정한다면 두 종류의 조회 권한을 나눠야 합니다

이번 작업에서는 서비스를 수정하거나 재배포하지 않았습니다. 아래는 확인한 동작을 바탕으로 정리한 수정안과 통과 기준입니다.

점주용 조회는 서버가 로그인 정보에서 회원 ID를 얻고, 주문의 가맹점 소유자와 함께 조회해야 합니다. 클라이언트가 보내는 `merchantId`를 신뢰하거나 화면에서 다른 주문 링크를 숨기는 것으로는 충분하지 않습니다. 주문 코드와 로그인 회원의 소유 관계가 맞지 않으면 데이터를 반환하지 않아야 합니다.

비회원 영수증 조회는 별도 경로와 권한으로 다루는 편이 명확합니다. 주문 생성 시 암호학적으로 안전한 임의의 조회 토큰을 발급하고, 주문과 연결해 만료·철회 조건을 검사해야 합니다. 표시용 주문 코드는 계속 사용할 수 있지만 그 자체가 접근키가 되면 안 됩니다. 토큰은 로그와 분석 도구에 노출되지 않도록 처리하고, 응답도 손님에게 필요한 필드로 제한해야 합니다.

반복 요청 제한과 이상 조회 탐지는 보조 방어입니다. 조회 권한 검사가 없는 상태에서 횟수 제한만 추가하면, 적은 수의 무단 조회는 여전히 가능합니다. 로그인 여부, 주문 소유 관계, 비회원 조회 권한을 먼저 분리해야 합니다.

수정 후에는 기존 두 더미 주문을 그대로 두고 다음 결과를 확인하면 됩니다.

| 재검증 조건 | 기대 결과 |
| --- | --- |
| A가 점주용 경로에서 A 주문 조회 | 200, A 주문 반환 |
| A가 점주용 경로에서 B 주문 조회 | 403 또는 존재를 감추는 404, 주문 본문 없음 |
| 비인증 요청이 점주용 경로 조회 | 401, 주문 본문 없음 |
| 올바른 비회원 조회 토큰으로 연결된 주문 조회 | 200, 필요한 영수증 정보만 반환 |
| 조회 토큰 없이 표시용 주문 코드만 전달 | 주문 상세 반환 안 됨 |
| A 주문 조회 토큰으로 B 주문 요청 | 주문 상세 반환 안 됨 |
| 만료·철회된 조회 토큰 사용 | 주문 상세 반환 안 됨 |
| A/B의 자기 매장 테이블 목록 조회 | 각각 자기 주문만 반환하는 기존 동작 유지 |

HTTP 코드만 바뀌었는지 보지 않고, 오류 응답에 주문·메뉴·금액이 남아 있지 않은지도 확인해야 합니다. 비회원 정상 주문 흐름이 깨지지 않는지까지 함께 검증해야 수정이 끝납니다.

## 증거와 테스트 데이터 관리

이번 실행은 ARTEX의 작업·Worker 기록과 로컬 `evidence.json`으로 남겼습니다. 스크린샷은 실제 ARTEX 화면을 촬영했고, 표는 그 명령 출력과 증거 파일을 대조해 작성했습니다. 영상은 촬영하지 않았습니다. 스크린샷만으로 모든 응답을 보여주기 어려워 요청별 해시와 비교 결과도 함께 보존했습니다.

서버 측까지 같은 사건을 연결하려면 API 접근 로그에 요청 시각, 메서드, 경로 템플릿, 상태, 인증된 회원의 내부 식별자, 요청 ID를 남기는 것이 좋습니다. Authorization·Cookie·비밀번호와 비회원 조회 토큰 원문은 제외해야 합니다. 이번 실행에서 서버 로그를 직접 수집한 것은 아니므로 요청 시각 비교 시 Mac과 Windows의 시계 차이도 고려해야 합니다.

생성한 회원·가맹점·테이블·메뉴·주문은 수정 후 재검증에 사용할 수 있도록 유지했습니다. 계정 접두어는 `artex_20261020_002744_`이고 위 표에 해당 식별자를 기록했습니다. 임의로 주문을 취소하거나 환불해 정리하지 않았습니다. 테스트 DB에서 정리할 때도 이 식별자와 외래키 관계를 확인하고 해당 더미 데이터만 제거해야 합니다. 로그인 비밀번호 파일은 로컬에서만 보관하고 블로그 저장소에는 포함하지 않았습니다.

처음의 질문에 대한 답은 분명했습니다. **이번 환경에서는 주문 코드만 알면 로그인하지 않아도 해당 더미 주문의 상세를 읽을 수 있었습니다.** 목록 API의 인증 거절만 보고 점검을 끝내지 않고, 실제 데이터를 만든 뒤 같은 주문의 여러 접근 경로를 비교한 이유입니다.
