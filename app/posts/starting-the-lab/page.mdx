현재 GLN에 입사해 금융 관련 업무를 하고 있습니다. 업무를 익히면서 계좌, 송금, 환율, 정산처럼 자주 접하는 개념을 조금 더 깊이 이해하고 싶어졌습니다. 용어의 의미를 아는 데서 한 걸음 더 나아가, 이 기능들을 직접 만든다면 어떤 문제를 만나게 될지 궁금했습니다.

그래서 작은 은행을 만드는 사이드 프로젝트를 시작하려고 합니다. 계좌를 만들고 같은 은행 안에서 돈을 옮기는 것부터 시작해, 다른 은행과의 송금, 분산 트랜잭션, 해외송금까지 범위를 넓혀볼 생각입니다.

이 블로그에는 그 과정에서 선택한 설계와 선택 이유, 직접 측정한 결과를 남기려고 합니다. 첫 번째 글에서는 앞으로 무엇을 만들고, 어떤 질문을 확인할지 정리했습니다. **아래 내용은 앞으로 진행할 실험 계획이며, 아직 구현하거나 측정한 결과는 아닙니다.**

## 금융 실험실에서 확인하고 싶은 것

가장 먼저 떠오른 질문은 간단합니다. **동시에 돈을 보내도 잔액이 정확하게 유지될까요?** 여기서 출발하면 다음 질문들이 이어집니다.

- 같은 계좌에 요청이 몰리면 비관적 락과 낙관적 락 중 어떤 방식이 유리할까요?
- 출금은 끝났는데 상대 은행의 응답을 받지 못했다면, 이 송금은 어떤 상태일까요?
- 서비스를 나눴을 때 한쪽만 성공한 거래는 누가 끝까지 책임져야 할까요?
- 해외송금의 메시지 전달, 환전, 실제 자금 결제는 어떻게 연결될까요?
- 거래가 늘거나 장애가 발생해도, 돈의 흐름을 설명하고 복구할 수 있을까요?

금융 도메인과 시스템 설계를 함께 이해하는 개발자로 성장하는 것이 목표입니다. 새로운 기술을 적용할 때도 어떤 문제를 해결했고, 그 대가로 어떤 복잡성과 비용이 생겼는지 설명할 수 있었으면 합니다.

## 01. API 계약부터 정하기

처음에는 토스처럼 개발자 문서가 잘 정리된 서비스를 참고해 은행 API를 설계하려고 했습니다. 다만 공개된 **토스페이먼츠 문서는 결제 API**이므로, 이를 은행 내부의 코어뱅킹 명세와 동일하게 볼 수는 없습니다. 요청과 응답을 설명하는 방식, 오류 처리, 멱등키처럼 API 계약을 설계하는 관점에서 참고하려고 합니다. [토스페이먼츠의 멱등키 문서](https://docs.tosspayments.com/reference/using-api/authorization)에서는 같은 요청을 다시 보내는 경우의 처리 규칙을 확인할 수 있습니다.

은행 외부 연계는 [금융결제원의 오픈뱅킹 API](https://developers.kftc.or.kr/dev/openapi/open-banking/deposit)를 함께 살펴볼 예정입니다. 공개 API로 확인할 수 있는 범위와 은행 내부에서 직접 설계해야 하는 범위를 나누겠습니다.

SSAFY에서 제공받았던 금융 API 명세도 출발점 후보입니다. 다시 검토해 계좌·이체 기능을 참고하되, 필요한 부분은 이 프로젝트에 맞게 새로 정의하려고 합니다. **현재 그 명세를 검토해 기준으로 확정한 상태는 아닙니다.**

첫 명세에는 계좌 개설, 잔액·거래 조회, 당행 이체, 이체 결과 조회를 담겠습니다. 정상 응답 외에도 다음 내용을 먼저 정할 생각입니다.

- 금액과 통화의 표현, 거래번호와 요청 멱등키의 역할
- 같은 키·같은 요청의 재전송과, 같은 키·다른 요청의 충돌 처리
- 접수·처리 중·완료·거절·결과 미확정 상태와 허용되는 상태 전이
- 타임아웃 후 결과 조회, 재시도 가능 여부, 오류 코드의 의미

**완료 기준은 OpenAPI 문서만 보고 정상·중복·실패 시나리오를 재현할 수 있는 것입니다.** 이후 구현과 문서가 어긋나지 않도록 계약 테스트도 연결하겠습니다.

## 02. 계좌와 원장을 가진 작은 은행 만들기

첫 구현은 은행 A 하나입니다. 하나의 애플리케이션 안에서 계좌·원장·이체 모듈을 구분하고, 하나의 관계형 DB에서 트랜잭션을 처리하는 구조로 시작하려고 합니다. 나중에 구조를 바꾸더라도 비교할 수 있는 기준점이 필요하기 때문입니다.

여기서 가장 먼저 설계할 대상은 잔액을 설명하는 기록입니다. 계좌의 현재 잔액과 거래를 기록하는 원장을 구분하고, **분개마다 통화별 차변 합계와 대변 합계가 맞는 복식부기 모델**을 실험용으로 구성하겠습니다. 고객 예금과 은행의 자산·부채 계정도 구분해, 고객 간 송금과 외부 입출금을 같은 방식의 단순 증감으로 뭉뚱그리지 않으려고 합니다.

원장은 잔액의 변경 근거를 남기고, 현재 잔액은 거래 처리에 사용할 값으로 관리하겠습니다. 확정된 기록을 고치는 대신 원거래를 참조하는 역분개로 정정하는 방식을 검토할 예정입니다. 테스트용 초기 자금도 대응 계정을 가진 기록으로 남겨, 나중에 잔액을 다시 계산할 수 있게 하겠습니다.

초기 범위는 계좌 개설·상태 관리, 모의 입출금, 잔액·거래 조회, 당행 이체입니다. 대출이나 이자 계산은 뒤로 미루고, 통화별 소수 자릿수와 반올림 규칙부터 명시하겠습니다.

**완료 기준은 원장에서 계산한 잔액과 저장된 잔액이 일치하고, 금지한 초과 출금·불균형 분개·거래 중복을 검출하는 것입니다.** 정상 거래뿐 아니라 중간 실패와 정정 거래도 검증하겠습니다.

## 03. 동일 은행에서 동시 이체와 락 비교하기

기능이 동작하면 같은 계좌에 여러 출금 요청을 동시에 보내보려고 합니다. 비관적 락과 낙관적 락의 비교는 이 단계에서 시작하겠습니다. 타행 연계까지 한 번에 섞으면 네트워크 지연과 로컬 DB 경합 중 무엇이 결과에 영향을 줬는지 구분하기 어렵기 때문입니다.

| 비교 대상 | 구현에서 확인할 점 | 주로 측정할 비용 |
| --- | --- | --- |
| 비관적 락 | 필요한 행을 잠근 뒤 잔액 검증·변경, 계좌 잠금 순서 통일 | 락 대기, 교착 상태, 긴 트랜잭션 |
| 낙관적 락 | 버전 검증 실패 시 트랜잭션 전체를 제한적으로 재시도 | 충돌률, 재시도 횟수, 최종 지연 |
| 조건부 UPDATE | 잔액 조건과 변경을 한 문장에 적용하고 영향 행 수 확인 | 경합 시 대기, 갱신 실패율 |

조건부 UPDATE도 DB 내부의 락을 사용하므로 무잠금 방식으로 부르지 않겠습니다. 세 방식 모두 출금·입금·분개를 같은 로컬 트랜잭션으로 묶어 비교할 계획입니다. PostgreSQL의 [행 잠금과 교착 상태 설명](https://www.postgresql.org/docs/17/explicit-locking.html)을 확인하면서 양방향 이체도 재현하겠습니다.

부하는 여러 계좌에 고르게 분산되는 경우, 소수 계좌에 집중되는 경우, A→B와 B→A가 동시에 발생하는 경우로 나누겠습니다. 락 전략만 바꾼 실험과 격리 수준을 바꾼 실험도 분리할 생각입니다.

**완료 기준은 잔액·원장 불일치가 없는 조건에서 처리량과 지연, 충돌·재시도 비용을 비교하는 것입니다.** 단순히 “낙관적 락이 빠르다”로 끝내지 않고 어느 정도의 경합에서 결과가 달라지는지 남기겠습니다.

## 04. 은행 B를 만들고 타행 송금 연결하기

다음에는 은행 B를 별도 프로세스와 DB로 구성하겠습니다. 두 은행이 같은 DB나 테이블을 공유하지 않게 하고, 은행별 API와 중계 역할을 가진 모의 시스템을 연결할 예정입니다.

이때부터는 은행 A의 DB 트랜잭션만으로 은행 B의 처리까지 원자적으로 묶을 수 없습니다. A에서 출금한 뒤 B로 요청을 보냈는데 응답을 받지 못했다면, B가 아직 처리하지 않았을 수도 있고 처리를 마친 뒤 응답만 유실됐을 수도 있습니다. **타임아웃만으로 실패를 확정하거나 즉시 돈을 돌려주지 않고, 거래번호로 결과를 확인하는 절차**를 설계하려고 합니다.

오픈뱅킹은 이 과정에서 이용기관·중계·참가은행의 역할을 이해하는 참고 모델로 다루겠습니다. 금융결제원 입금이체 문서는 약정 계좌, 거래고유번호, API와 참가은행의 응답을 구분합니다. 이 외부 계약을 참고해 모의 연계를 만들되, 제가 만든 A→B HTTP 호출을 실제 국내 타행 결제망 전체와 동일하게 설명하지는 않겠습니다.

고객의 송금 처리와 은행 사이의 결제도 나누겠습니다. 은행별 결제 계정과 미결제 금액을 기록하고, 개별 거래를 결제하는 모델과 일정 구간의 금액을 차감해 결제하는 모델을 실험하려고 합니다. 이후 은행 A·B·중계 기록을 비교하는 대사 배치로 누락과 불일치를 찾아보겠습니다.

**완료 기준은 중복 요청·응답 유실·지연 응답 이후에도 거래를 추적하고, 미확정 거래를 조회·대사·재처리로 정리하는 것입니다.** 특정 은행의 응답이 늦어질 때 다른 거래까지 얼마나 영향을 받는지도 측정하겠습니다.

## 05. 하나의 은행을 MSA로 분리하기

타행 송금의 기본 흐름을 만든 뒤에는 은행 A를 비교 기준으로 유지하고, 은행 B의 내부를 마이크로서비스 구조로 바꿔볼 생각입니다. 같은 업무 시나리오를 두 구조에서 실행해 기능 검증과 운영 비용을 비교하겠습니다.

처음부터 모든 테이블을 서비스로 나누지는 않겠습니다. 계좌·원장의 강한 일관성이 필요한 부분은 한 경계 안에 두고, 송금 처리·은행 연계·알림처럼 책임이 다른 영역부터 분리하려고 합니다. 서비스별 데이터 소유권을 정하고 다른 서비스의 DB를 직접 수정하지 않겠습니다.

내부 통신은 HTTP, gRPC, 비동기 메시징을 검토하겠습니다. HTTP와 gRPC는 같은 요청·응답 계약으로 비교하고, 메시징은 접수 응답 시간과 실제 업무 완료 시간을 따로 측정하겠습니다. 프로토콜을 바꾼 효과와 서비스 분리로 호출 횟수가 늘어난 효과도 구분하겠습니다.

이벤트를 쓰는 경우에는 DB 변경과 이벤트 발행 사이의 누락을 다뤄야 합니다. [Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)를 적용해 업무 데이터와 발행할 이벤트를 같은 DB 트랜잭션에 기록하고, 소비 측에서는 이벤트 식별자로 중복 처리를 막겠습니다. Outbox 자체가 여러 서비스의 업무 트랜잭션을 완성해주는 것은 아니므로 다음 단계의 Saga와 함께 검증할 예정입니다.

**완료 기준은 서비스 분리 이후에도 기존 정합성 검증을 통과하고, 통신 비용·이벤트 지연·장애 전파 범위를 설명하는 것입니다.** MSA 전환으로 얻은 독립성과 추가된 운영 부담을 함께 남기겠습니다.

## 06. 분산 트랜잭션을 구현하고 실패시켜 보기

분산 트랜잭션은 별도의 실험 주제로 깊게 다루고 싶습니다. 먼저 **Saga 오케스트레이션을 담당하는 전용 서비스**를 만들고, 같은 업무 흐름을 다른 방식으로도 구현해보겠습니다.

오케스트레이터는 거래 단계와 결과를 영속화하고, 중간에 종료돼도 미완료 작업을 이어갈 수 있어야 합니다. 송금 흐름에서는 자금 예약·외부 처리·확정 또는 해제 단계를 모델링하겠습니다. 이미 확정된 입금처럼 쉽게 되돌릴 수 없는 지점도 명시하고, 결과 미확정 상태에서는 조회와 대사를 먼저 수행하도록 하겠습니다.

| 방식 | 실험할 내용 | 실패 시 확인할 질문 |
| --- | --- | --- |
| Saga 오케스트레이션 | 중앙 서비스가 상태와 다음 작업을 관리 | 오케스트레이터가 재시작해도 이어갈 수 있을까? |
| Saga 코레오그래피 | 각 서비스가 이벤트에 반응해 다음 단계 수행 | 누락·순서 역전과 순환 의존을 어떻게 추적할까? |
| TCC | Try에서 자원을 예약하고 Confirm/Cancel로 확정·해제 | 예약 만료, 중복 확정, 늦게 도착한 취소를 어떻게 다룰까? |
| 2PC | 통제 가능한 DB 참여자와 코디네이터로 prepare/commit 실험 | 준비된 거래와 락이 남으면 어떻게 결정·복구할까? |

Saga의 보상은 이미 커밋된 작업의 영향을 업무적으로 상쇄하는 별도 거래입니다. DB 롤백과 같지 않고, 보상 자체도 실패할 수 있습니다. [AWS의 Saga 설명](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)을 바탕으로 보상 재시도와 운영자 확인이 필요한 상태까지 모델링하려고 합니다.

2PC는 참여자가 해당 프로토콜을 지원하는 실험 환경에서만 비교하겠습니다. PostgreSQL의 [준비된 트랜잭션](https://www.postgresql.org/docs/16/sql-prepare-transaction.html)을 활용할 수 있지만, 독립된 외부 은행의 API를 호출한다고 그 은행을 2PC 참여자로 만들 수 있는 것은 아닙니다.

각 방식의 보장 수준이 다르므로 TPS 숫자 하나로 순위를 매기지는 않겠습니다. 같은 업무 목표 아래에서 **거래 확정 시점, 중간 상태의 노출, 장애 후 수렴 시간, 예약·락 점유, 재처리 부담**을 나눠 비교하겠습니다.

**완료 기준은 모든 주요 단계에서 프로세스를 종료하거나 메시지를 중복 전달해도, 거래를 중복 확정하지 않고 복구 경로를 설명할 수 있는 것입니다.** 자동 복구가 불가능한 거래도 누락 없이 식별해야 합니다.

## 07. 해외송금과 SWIFT로 범위 넓히기

국내 송금 흐름을 이해한 뒤에는 서로 다른 통화를 사용하는 금융기관을 추가하겠습니다. 환율 견적을 발급하고, 견적의 유효기간 안에서 송금을 접수한 뒤, 환전·수수료·해외 지급·정산을 연결하는 모델을 만들 계획입니다.

이 단계에서는 SWIFT를 메시지 관점에서 이해하려고 합니다. [SWIFT의 공식 설명](https://www.swift.com/about-us/who-we-are)에 따르면 SWIFT는 금융기관 간 지급 지시 등을 전달하는 메시징 시스템이며, 직접 돈을 보유하거나 옮기는 은행은 아닙니다. 따라서 메시지 접수·전달 상태와 실제 자금 결제 상태를 별도로 기록하겠습니다.

메시지는 ISO 20022를 중심으로 살펴보겠습니다. SWIFT는 CBPR+ 지급지시의 MT·ISO 20022 공존 기간이 2025년 11월 종료됐다고 안내하고 있습니다. [관련 안내](https://www.swift.com/standards/iso-20022/iso-20022-bytes)를 기준으로, MT103은 기존 구조를 이해하는 비교 대상으로 다루고 `pacs.008`의 송금 정보, `pacs.002`의 상태 보고, `pacs.004`의 반환 흐름을 학습 범위로 잡겠습니다. 실제 네트워크 접속 대신 공개 설명을 참고한 모의 메시지 교환부터 구현하겠습니다.

환율과 자금 흐름에서는 다음 조건을 확인하려고 합니다.

- 기준 환율과 고객 적용 환율, 스프레드·수수료·통화별 반올림
- 견적 만료와 재견적, 출금 통화와 수취 통화의 금액 관계
- 상대 은행에 보유한 계정인 Nostro와 상대 은행 계정을 보는 Vostro 관점
- 사전 예치 자금 부족, 중개기관, 영업일·시차·마감 시간의 영향
- 가상의 고객확인·제재 검사 결과에 따른 보류, 승인, 반환

**완료 기준은 한 건의 해외송금에 대해 메시지, 환율, 통화별 분개, 외부 결제 상태를 연결해 설명하는 것입니다.** 서로 다른 통화의 금액을 그대로 합산해 잔액 보존을 판단하지 않고, 환전 대응 계정과 적용 환율을 함께 검증하겠습니다.

## 08. 운영과 복구까지 검증하기

마지막에는 거래가 계속 쌓이고 일부 구성 요소가 멈추는 환경을 만들겠습니다. 거래번호를 기준으로 로그·메트릭·분산 추적을 연결하고, 정상 처리 속도와 함께 **가장 오래 남은 미완료 거래가 무엇인지** 확인할 수 있게 하겠습니다.

장애 실험은 응답 지연·응답 유실, DB 장애, 브로커 중단, 소비자 재시작, 배포 중 종료로 나누겠습니다. 백업에서 복원한 뒤 원장과 잔액을 대조하고, 이벤트 재처리가 중복 반영을 만들지 않는지도 확인하겠습니다. RTO는 복구에 걸리는 시간, RPO는 복구 시 허용하는 데이터 손실 구간으로 정의해 실제 관측값을 남기겠습니다.

API 인증·권한, 계좌번호와 로그의 마스킹, 비밀값 관리, 감사 기록도 검증 대상입니다. 민감정보를 기록하지 않으면서 거래를 추적할 수 있는지, 재처리 권한과 변경 이력을 어떻게 남길지 살펴보겠습니다.

**완료 기준은 장애를 재현하고, 미완료 거래를 찾아 복구한 뒤, 원장 검증으로 결과를 확인하는 절차를 다른 사람도 따라 할 수 있는 것입니다.**

기본 실험이 쌓이면 조회 모델을 분리하는 CQRS, 이벤트를 원본 기록으로 사용하는 이벤트 소싱, 파티셔닝·샤딩과 CDC도 확장 주제로 검토하겠습니다. 모두 한 번에 적용하지 않고, 조회 병목이나 복구 문제처럼 필요성이 확인된 주제부터 비교할 생각입니다.

## 성능은 어떤 조건에서 비교할까?

실험마다 환경이 달라지면 숫자를 비교하기 어렵습니다. 아래는 측정을 시작하기 위한 **초기 후보 조건**입니다. 목표 성능이나 이미 달성한 수치가 아니며, 실행 환경의 자원 한계를 확인하면서 조정하겠습니다.

| 축 | 초기 실험 조건 |
| --- | --- |
| 데이터 규모 | 계좌 1만·10만 개, 원장 항목 10만·100만·1,000만 건을 단계적으로 준비 |
| 동시성 | 동시 요청 1·10·50·100부터 시작해 포화 구간 탐색 |
| 도착률 | 초당 요청 수를 별도로 고정·증가시켜 큐 적체와 거절 관찰 |
| 계좌 경합 | 균등 분산 / 요청 80%가 계좌 1%에 집중 / 단일 계좌 집중 |
| 거래 패턴 | 단방향·양방향 이체, 조회·이체 혼합, 중복 요청 |
| 장애 조건 | 정상 / 추가 지연 / 처리 후 응답 유실 / 확정 전후 프로세스 종료 |
| 반복 | 워밍업 후 같은 시드·데이터로 최소 5회, 실행 순서 교차 |

처리량은 **최종 성공한 업무 거래 수/초**로 정의하고, HTTP 요청 수나 재시도 횟수와 구분하겠습니다. 지연 시간은 최초 요청부터 최종 결과까지 재시도를 포함해 측정하고, 비동기 방식에서는 접수 지연과 완료 지연을 함께 공개하겠습니다.

평균뿐 아니라 p50·p95·p99, 실패·타임아웃률, 락 대기, 충돌률, 재시도 횟수, CPU·메모리·DB I/O를 수집할 예정입니다. 원장 불균형·중복 반영·잔액 불일치 건수와 미확정 거래의 수·체류 시간도 같은 보고서에 담겠습니다.

비교할 때는 자원 한도, DB·런타임 버전, 커넥션 풀, 인덱스, 격리 수준, 네트워크 조건을 기록하겠습니다. 구조를 비교할 때는 전체 자원 예산을 맞추고 서비스·DB별 배분도 공개하겠습니다. 부하 생성기가 먼저 한계에 도달하거나, 시스템이 느려져 요청 생성까지 줄어드는 착시가 없는지도 확인하겠습니다.

각 실험에는 코드 커밋, 데이터 생성 시드, 실행 명령, 원본 측정값, 그래프와 설계 결정을 함께 남기려고 합니다. 여러 변수의 전체 조합을 한 번에 돌리기보다, 기준 실험에서 한 축씩 바꾸고 결과가 달라지는 구간을 좁혀가겠습니다.

## 첫 출발은 작게

로드맵은 길지만, 첫 구현 범위는 **은행 A의 계좌 개설·원장·당행 이체**입니다. 먼저 잔액을 설명할 수 있는 모델과 실패 조건을 정하고, 그 위에서 동시성 실험을 시작하겠습니다.

이 프로젝트는 공개 자료와 가상의 거래 데이터를 사용하는 개인 실험입니다. 회사 내부 구현을 재현하거나 실제 금융기관과 동일한 시스템이라고 전제하지 않고, 확인한 공개 동작과 실험을 위해 단순화한 가정을 글마다 구분하려고 합니다.

앞으로 남길 글에서는 하나의 질문을 정하고, 구현하고, 실패시켜보고, 측정한 결과를 설명하겠습니다. 이 기록이 쌓였을 때 새로운 금융 기술을 접하더라도 적용 조건과 한계를 스스로 판단할 수 있기를 기대합니다.
