2026년 10월, 금융권에서 개인정보 유출과 침해사고가 연이어 보도됐다. 처음에는 개별 금융회사의 사고로 보였지만, 후속 발표를 보며 문제가 특정 회사나 특정 업권에 국한되지 않는다는 점에 더 주목하게 됐다.

[2026년 10월 14일 금융당국 발표를 전한 연합뉴스 보도](https://www.yna.co.kr/view/AKR20261014134852002)에 따르면, 금융권 침해사고는 총 **16개 금융회사**에서 발생했으며 **약 10만 건의 개인정보 유출**이 파악됐다.

[OK저축은행에서도 대출 신청 페이지를 통한 비인가 접근이 탐지](https://www.newsis.com/view/NISX20261013_0003824586)됐고, 고객 **183명의 개인정보 유출 가능성**이 신고됐다. 해당 정보조회시스템은 차단 조치가 이루어졌으며, 유출 경위에 대한 조사가 진행됐다.

이러한 사고를 살펴보면서 **핵심 금융시스템뿐만 아니라 외부에 노출된 웹 서비스와 API 역시 중요한 보안 점검 대상**이라는 점에 관심이 갔다. [브릿지경제의 외부 서비스 보안 사각지대 보도](https://www.viva100.com/article/20261012500772)와 [금융당국의 긴급 점검 관련 보도](https://www.etnews.com/20261014000009)도 이런 문제의식을 더했다.

여기서 한 가지 질문이 생겼다.

**정상적인 주문과 결제가 동작하도록 만들었던 내 서비스는, 허용되지 않은 요청까지 제대로 구별하고 있을까?**

## AI 보안 테스트 도구 ARTEX

최근 관심 있게 본 도구 중 하나가 [ARTEX](https://github.com/Autumn-27/ARTEX)다. AI를 활용해 보안 점검을 자동화하는 도구다.

[10월 6일 연합뉴스 보도](https://www.yna.co.kr/amp/view/AKR20261006118100017)는 안랩이 ARTEX 관련 운영 인프라 정황을 분석했다고 전했다. 이후 [10월 10일 보도](https://www.yna.co.kr/view/AKR20261010022500017)에 따르면 개발자는 악용 우려로 공개 개발을 중단하고 추가 버전을 공개하지 않겠다고 밝혔다.

이 소식을 접하면서 **이런 도구를 방어적 관점에서 직접 사용해보면 어떨까** 하는 궁금증이 생겼다.

이번에는 MacBook에서 ARTEX와 **Ollama의 `qwen3:8b` 모델**을 사용하고, 같은 네트워크에 연결된 Windows 노트북에서 과거 개발했던 서비스를 실행해 보안 테스트를 진행할 계획이다.

## 왜 원큐오더인가?

대상은 우리 FIS 아카데미에서 개발했던 [원큐오더(WON-Q Order)](https://github.com/won-q)다. 테이블 QR을 통한 비회원 주문과 결제, 가맹점의 주문 관리를 구현한 프로젝트다.

원큐오더는 단일 API 서버만으로 구성된 프로젝트가 아니었다. 주문 서비스와 PG, 앱카드, 카드사 및 은행 역할의 서버가 협력해 결제 흐름을 구성한다. 여기서 카드사·은행 서버는 **프로젝트 내부에서 금융기관 역할을 모의한 구성 요소**이지, 실제 금융기관의 운영 시스템이 아니다.

직접 설계와 개발에 참여했던 프로젝트라 코드를 읽을 수 있고, 테스트 데이터를 만들고, 문제를 발견하면 수정한 후 같은 조건으로 재검증할 수 있다. 무엇보다 정상 주문과 결제를 만드는 데 집중했던 당시의 관점에서 벗어나, **예상하지 않은 요청을 시스템이 어디에서 어떻게 거부하는지** 살펴보고 싶었다.

## 테스트 환경과 아키텍처

WON-Q Order는 기존에 Kubernetes 환경에서 개발·배포했던 프로젝트다. 이번에는 좀 더 간단하게 실험할 수 있도록 로컬 환경으로 옮겨볼 생각이다.

MacBook에서는 **ARTEX와 Ollama(`qwen3:8b`)**를 실행하고, 동일한 네트워크의 Windows 노트북에는 **WON-Q Order의 주문·결제 서비스와 모의 카드사·은행 서버**를 배포할 예정이다.

## 앞으로 해볼 것

우선 Windows에서 WON-Q Order의 주문부터 결제·환불까지 정상적으로 동작하도록 환경을 구성할 생각이다. 이후 MacBook의 ARTEX를 연결해 **외부에 노출된 API, 인증·인가, 주문과 결제 처리 과정**을 중심으로 보안 테스트를 진행하려고 한다.

특히 다른 가맹점의 주문에 접근하려는 요청이나 중복 결제·환불 요청처럼, 평소 정상적인 사용 흐름에서는 놓치기 쉬운 상황을 살펴볼 예정이다.

그 과정에서 ARTEX가 어떤 방식으로 문제를 찾아가는지 기록하고, 실제 문제가 발견된다면 원인 분석부터 코드 수정과 재검증까지 이어갈 생각이다. 환경 구성과 테스트 과정, 결과는 다음 글에서 다뤄보려고 한다.
