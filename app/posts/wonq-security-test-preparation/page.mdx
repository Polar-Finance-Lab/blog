2026년 10월, 금융권의 개인정보 유출 관련 보도가 연이어 나왔다. 그중 특히 눈에 들어온 것은 금융 서비스의 **대출 신청 페이지나 외부 연계 서비스처럼, 이용자와 맞닿아 있는 접점**이 점검 대상이 되고 있다는 점이었다.

[전자신문은 10월 13일 OK저축은행의 대출 신청 페이지를 통해 고객 183명의 개인정보가 유출됐다는 정황을 보도](https://www.etnews.com/20261013000442)했다. 후속 보도에 따르면 10월 12일 해당 페이지에서 비인가 접근이 탐지되자 정보조회시스템을 차단하고 금융당국에 신고했으며, 외부 보안 전문업체와 함께 유출 경위를 조사했다. [10월 14일 보도](https://www.dailian.co.kr/news/view/1701245/%EA%B8%88%EC%9C%B5%EA%B6%8C-%ED%95%B4%ED%82%B9-%ED%99%95%EC%82%B0OK%EC%A0%80%EC%B6%95%EC%9D%80%ED%96%89-%EA%B3%A0%EA%B0%9D-1-2026)에서도 실제 유출 여부를 조사 중이라고 설명했다. 언론별로 '유출 확인'과 '유출 가능성'의 표현에 차이가 있어, **183명은 당시 보도된 잠정 규모이며 구체적인 침투 원인과 최종 피해 범위는 확정된 것으로 단정하지 않았다.** [브릿지경제는 저축은행의 외부 서비스 보안 관리 문제](https://www.viva100.com/article/20261012500772)를 짚었고, [전자신문은 금융당국의 긴급 점검 움직임](https://www.etnews.com/20261014000009)을 전했다.

여기서 내가 주목한 것은 특정 금융사의 사고 자체보다, **서비스의 경계에서 인증과 권한 검증이 얼마나 일관되게 적용되는가**라는 질문이었다.

웹 화면에서 로그인이 되어 있는지, API가 정상 응답하는지만 확인해서는 충분하지 않다. 다른 사용자의 주문을 조회하거나, 권한이 없는 가맹점의 결제를 변경하려는 요청도 서버가 제대로 거부해야 한다. 특히 주문과 결제처럼 여러 서비스가 연결된 경우에는 화면의 성공·실패뿐 아니라 실제 거래 상태가 바뀌었는지까지 확인해야 한다.

보안업계의 최근 분석 자료도 공통적으로 외부에 노출된 서비스와 API의 관리, 서버 측 인증·인가 검증, 변화하는 시스템을 주기적으로 다시 점검하는 필요성을 강조하고 있었다. 자료에 포함된 비공개 분석 내용이나 구체적인 공격 정보는 옮기지 않고, 내가 개발한 서비스에 적용할 수 있는 **일반적인 점검 관점**만 가져오기로 했다.

이 글은 실제 금융사에 대한 공격이나 사고 원인 분석이 아니다. 공개 보도를 계기로 **과거에 직접 개발한 결제 서비스를 다시 검증해보려는 준비 기록**이다.

## AI가 이 점검을 도울 수 있을까?

최근 관심 있게 본 도구 중 하나가 [ARTEX](https://github.com/Autumn-27/ARTEX)다. AI를 활용해 보안 점검 작업을 계획·수행하도록 돕는 오픈소스 도구로 알려져 있다.

금융권 사고 관련 보도와 보안업계 분석에서는 AI를 활용한 공격 자동화 가능성도 거론됐다. 다만 **특정 사고에서 ARTEX가 실제 공격 도구로 사용됐다는 사실이 확정된 것은 아니다.** 공격 관련 정황과 도구의 실제 사용 여부는 구분해 볼 필요가 있다.

내가 알고 싶은 것도 'AI가 해킹에 성공하는가'라는 한 문장으로 끝나지 않는다.

- AI가 API의 인증·인가 경계를 이해하고 검증할 만한 질문을 제시할 수 있을까?
- 정상적인 기능 오류와 실제 보안 문제를 구분할 수 있을까?
- 발견했다고 주장하는 문제를 같은 조건에서 다시 재현할 수 있을까?
- 수정 이후 정상 거래는 유지하면서 비정상 요청만 차단되는지 검증할 수 있을까?

이번 실험에서는 ARTEX를 **보안 테스트 보조 도구**로 사용한다. 모델이 출력한 판단은 가설로 두고, 최종 결론은 실제 요청·응답과 서비스 상태를 확인해 내릴 생각이다.

모델은 [Ollama](https://ollama.com/)를 활용해 로컬에서 실행하는 방향을 검토하고 있다. `qwen3:8b`는 후보일 뿐이며, 실제 설치·도구 연동·성능 검증이 끝난 구성은 아니다.

## 왜 원큐오더인가?

대상은 우리 FIS 아카데미에서 개발했던 [원큐오더(OneQOrder)](https://github.com/won-q)다. 테이블 QR을 통한 비회원 주문과 결제, 가맹점의 주문 관리를 구현한 프로젝트다.

원큐오더는 단일 API 서버로 끝나지 않는다. 주문 서비스와 PG, 앱카드, 카드사 및 은행 역할의 서버가 협력해 결제 흐름을 구성한다. 여기서 카드사·은행 서버는 **프로젝트 내부에서 금융기관 역할을 모의한 구성 요소**이지, 실제 금융기관의 운영 시스템이 아니다.

직접 설계와 개발에 참여했던 프로젝트라 코드를 읽을 수 있고, 테스트 데이터를 만들고, 문제를 발견하면 수정한 후 같은 조건으로 재검증할 수 있다. 무엇보다 정상 주문과 결제를 만드는 데 집중했던 당시의 관점에서 벗어나, **예상하지 않은 요청을 시스템이 어디에서 어떻게 거부하는지** 살펴보고 싶었다.

## 테스트 환경과 아키텍처

기존 프로젝트는 Kubernetes 기반 개발·운영 환경을 활용했다. 이번에는 실험을 단순하게 재현할 수 있도록 별도의 로컬 테스트 환경을 준비하고 있다.

**MacBook에서 ARTEX를 실행하고, 같은 로컬 네트워크에 연결한 Windows 호스트에 원큐오더 서비스를 배포**하는 구상이다. 외부 금융기관을 호출하는 대신 모의 서버와 더미 데이터만 사용한다.

{/* 아키텍처 이미지 삽입 위치: MacBook(ARTEX)과 Windows Host(OneQOrder/PG/AppCard/Card/Bank/Test DB)를 하나의 LAN 경계에 배치한 다이어그램. 실제 배포 결과 확인 후 이미지 경로 및 DB 연결 관계 확정. */}

현재 그려둔 구성도는 **배포 목표 구조**다. 서비스 간 실제 호출 방향과 데이터베이스 접근 관계는 Windows 배포 설정을 확인해 확정할 예정이다. 특히 한 개의 테스트 DB를 모든 서버가 공유한다고 단정하지 않고, 각 서비스의 실제 연결 설정을 먼저 확인하려고 한다.

두 장비가 같은 네트워크에 있다고 해서 보안 격리가 자동으로 보장되지는 않는다. 그래서 실험 전에 다음 조건을 확인하려고 한다.

- Windows의 테스트용 API 진입점에는 지정한 MacBook만 접근할 수 있도록 제한한다.
- 데이터베이스와 모의 카드·은행 서버 포트는 LAN에 직접 공개하지 않는다.
- 실제 외부 연동 주소와 자격증명은 테스트 전용 설정으로 교체한다.
- 임의로 만든 계정·주문·결제 정보만 사용하고, 복구 가능한 초기 상태를 준비한다.
- 필요한 의존성 준비 이후에는 불필요한 외부 통신을 차단한다.

이 조건들은 **현재 적용 완료된 보안 설정이 아니라 배포 전 확인할 체크리스트**다.

## 어떤 부분을 먼저 검증할까?

이번 점검은 무작정 취약점을 찾는 것보다, 서비스가 지켜야 할 규칙부터 명확히 정의하는 방식으로 진행하려고 한다.

우선 기존 저장소의 일부 코드를 검토했다. 분석 기준은 `api-server`의 `85ebd90`, `pg-server`의 `7f8af21`, `user-frontend`의 `9c16ba0` 커밋이다. 주문 API는 점주용 JWT 인증과 고객용 공개 기능이 공존하고, PG에는 가맹점 API 키와 관리자 인증 등 서로 다른 접근 경계가 있다. 이 구조를 기반으로 **인증 여부와 개별 객체에 대한 권한 검증을 나누어** 살펴보려고 한다.

| 확인할 상황 | 기대하는 결과 |
| --- | --- |
| 정상적인 주문·결제·환불 | 주문, 결제, 모의 거래 상태가 일치한다. |
| 가맹점 A가 B의 주문·메뉴에 접근 | 권한 없는 접근이 거부되고 B의 데이터는 변하지 않는다. |
| 서로 연결되지 않은 주문과 결제로 환불 요청 | 요청이 거부되고 결제·환불 효과가 발생하지 않는다. |
| 동일한 승인 또는 환불 요청 반복 | 거래 처리 효과가 중복 발생하지 않는다. |
| 승인 근거가 없는 결제 완료 요청 | 상태 변경이나 후속 승인 호출이 발생하지 않는다. |

첫 번째 단계는 공격 요청이 아니라 **정상적인 주문·결제·환불을 성공시키는 것**이다. 정상 동작이 확인되지 않으면, 비정상 요청이 실패했을 때 그것이 보안 규칙 때문인지 단순 기능 오류 때문인지 판단하기 어렵다.

가맹점 A와 B, 각 점주 계정, 메뉴, 주문, 결제는 모두 테스트용으로 생성하고 미리 알고 있는 식별자만 사용한다. 실제 고객 정보나 운영 서비스를 대상으로 무작위 탐색은 하지 않는다.

또한 HTTP 상태 코드가 거부됐다는 사실만으로 테스트를 통과시킬 생각은 없다. 예를 들어 화면에는 환불 실패가 표시됐어도 모의 은행 서버에 환불이 전달됐다면, 의도한 차단이 아니다. **API 응답, DB의 전후 상태, 모의 외부 서버의 호출 횟수**를 함께 확인해야 한다.

## ARTEX는 어디까지 맡길까?

ARTEX에 전체 네트워크를 자유롭게 탐색하도록 맡기기보다, 미리 정의한 API와 더미 계정에 대해 한 번에 하나의 가설을 검증하도록 계획하고 있다. 대상 주소·허용 동작·요청 상한·중단 조건을 명시하고, 프롬프트 외에도 네트워크 및 실행 환경 차원에서 범위를 강제할 예정이다.

실험 중 화면 동작은 Playwright 기반 테스트로 재현하는 방식도 검토하고 있다. 다만 Playwright MCP와 ARTEX의 실제 연동 가능 여부는 아직 확인하지 않았다.

결과에는 요청·응답, 대상 객체의 실행 전후 상태, 모의 카드·은행 서버의 처리 여부, 사용한 테스트 코드와 배포 커밋을 연결해 기록하려고 한다. 스크린샷과 trace, 로그에 포함될 수 있는 인증 정보는 공개 전에 별도로 확인하고 제거한다.

AI가 제시한 결과를 그대로 '취약점 발견'으로 게시하지도 않을 것이다. **재현 가능성, 실제 영향, 수정 전후의 차이, 정상 기능의 유지 여부**를 확인한 뒤 결론을 내릴 계획이다.

## 다음 단계

지금까지 완료한 것은 일부 저장소의 인증 경계를 살펴보고 실험 범위와 판정 기준을 정리한 일이다. Windows 배포, 서버 간 정상 연동, Ollama 및 ARTEX 실행, 실제 취약점 재현과 수정은 아직 진행·검증하지 않았다.

다음 글에서는 Windows에 서비스를 올리고, MacBook에서 테스트 대상에 접근할 수 있는지부터 확인하려고 한다. 그리고 정상적인 결제 흐름을 먼저 검증한 뒤, 가맹점 간 권한과 결제 상태 무결성에 대한 테스트로 범위를 넓혀갈 생각이다.

이번 실험에서 얻고 싶은 결과는 'AI가 몇 개의 취약점을 찾았다'는 숫자보다, **왜 문제가 생겼고 어떻게 막을 수 있는지 설명할 수 있는 검증 과정**이다.
