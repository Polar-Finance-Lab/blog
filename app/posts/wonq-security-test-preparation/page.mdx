직접 만든 주문·결제 서비스에서 정상적인 결제가 성공하는 것과, 허용되지 않은 결제가 차단되는 것은 다른 문제입니다. 다른 가맹점의 주문을 수정하려는 요청이나 이미 처리한 결제를 다시 승인하려는 요청까지 확인해야 서비스의 동작을 더 잘 이해할 수 있다고 생각했습니다.

그래서 제가 소유하고 관리하는 [원큐오더 프로젝트](https://github.com/won-q)를 별도의 테스트 환경에 배포하고 보안 점검을 진행하려고 합니다. MacBook에서 ARTEX를 활용하고, 같은 로컬 네트워크의 Windows 노트북에는 점검 대상 서비스를 올리는 구성입니다.

현재 Windows 환경은 준비 중입니다. 이번 글은 침투 테스트 결과나 취약점 발견 보고서가 아닙니다. 실행을 기다리는 동안 저장소를 살펴보고, 어떤 조건에서 무엇을 확인할지 정리한 준비 기록입니다.

## 먼저 테스트의 경계를 정했습니다

테스트 대상은 제가 통제하는 환경에 배포한 원큐오더와 직접 만든 더미 데이터로 한정했습니다. 실제 서비스, 다른 사람의 계정, 실제 카드·계좌 정보는 사용하지 않습니다. 목적은 서비스 장애를 만들거나 데이터를 가져오는 것이 아니라, 허용되지 않은 요청을 서비스가 제대로 구분하는지 확인하는 것입니다.

Mac과 Windows의 역할을 나눈 이유도 여기에 있습니다. 테스트 도구와 대상 서비스를 분리하면 요청이 어디서 시작됐고 어떤 서비스까지 도달했는지 추적하기 쉽습니다. 다만 컴퓨터를 나누거나 같은 LAN을 사용한다는 사실만으로 격리가 완성되지는 않습니다.

실행 전에 적용할 조건은 다음과 같이 정했습니다.

- Windows의 테스트용 진입점은 지정한 Mac에서만 접근하도록 제한합니다.
- DB와 내부 카드·은행 서비스 포트는 LAN에 직접 공개하지 않습니다.
- 실제 도메인과 외부 연동 주소는 테스트용 주소 또는 로컬 모의 서버로 바꿉니다.
- 테스트 전용 키와 데이터를 사용하고, 초기 상태로 돌아갈 수 있도록 스냅샷을 준비합니다.
- 의존성 준비가 끝난 테스트 런타임에서는 불필요한 외부 통신을 차단합니다.

이는 아직 적용 완료된 설정이 아니라, Windows 배포 전에 확인할 조건입니다. 특히 기존 설정에 남아 있는 외부 주소를 확인하는 일을 우선순위에 두었습니다. 테스트용 요청이라도 실제 외부 서비스에 전달되면 의도한 범위를 벗어나기 때문입니다.

## 저장소 이름보다 인증 경계를 먼저 살펴봤습니다

원큐오더는 하나의 서버로 끝나는 프로젝트가 아닙니다. 고객 화면과 점주 화면, 주문 API, PG, 앱카드, 카드사와 은행 역할의 구성 요소가 나뉘어 있습니다. 이 구분은 프로젝트 안에서 구현한 역할이며 실제 금융기관의 운영 구조를 그대로 재현했다는 의미는 아닙니다.

첫 분석에서는 다음 세 저장소의 코드를 기준으로 주문과 결제 경계를 살펴봤습니다.

| 저장소 | 분석 기준 커밋 | 확인한 부분 |
| --- | --- | --- |
| `api-server` | `85ebd90` | 주문 API의 공개 경로, JWT, 점주 소유권 검사 |
| `pg-server` | `7f8af21` | 가맹점 인증, 관리 권한, 결제 상태 처리 |
| `user-frontend` | `9c16ba0` | 브라우저에서 주문·결제를 요청하는 흐름 |

이 커밋들은 분석 기준입니다. Windows에 실제로 배포할 버전은 별도로 고정해야 합니다.

주문 API와 PG는 인증 방식이 같지 않았습니다. 주문 API에는 JWT를 사용하는 점주 기능과 고객이 접근하는 공개 기능이 함께 있었고, PG에는 가맹점 API 키 인증과 관리 사용자 JWT 인증이 구분되어 있었습니다. 별도의 Keycloak 예제 저장소가 있다는 이유만으로 전체 서비스가 Keycloak으로 보호된다고 가정하지도 않았습니다. [주문 API 보안 설정](https://github.com/won-q/api-server/blob/85ebd90c49d3773d1f2bcdac54a0106702134a8f/src/main/java/com/fisa/wonq/global/security/config/WebSecurityConfig.java)과 [PG 보안 설정](https://github.com/won-q/pg-server/blob/7f8af21a5fd59eb82514a085c46f827305993713/src/main/java/com/fisa/pg/config/security/SecurityConfig.java)을 나란히 놓고 확인했습니다.

이때 중요하게 본 것은 로그인 여부만이 아니었습니다. 로그인한 점주라도 다른 가맹점의 메뉴나 주문을 수정할 수 있어서는 안 됩니다. 인증된 사용자인지 확인하는 단계와, 그 사용자가 특정 객체를 다룰 권한이 있는지 확인하는 단계를 구분해서 봐야 했습니다.

코드에서 확인한 의심 지점은 실행할 테스트의 후보로 기록했습니다. 정적 분석만으로 실제 취약점이 재현됐다고 결론 내리지는 않았습니다. 다른 필터나 서비스에서 요청이 차단될 수도 있고, 반대로 정상 기능이 고장 나 있어서 모든 요청이 실패할 수도 있기 때문입니다.

## 첫 테스트는 공격 요청이 아니라 정상 결제입니다

가장 먼저 실행할 사례는 정상 주문, 결제, 환불입니다. 이 흐름이 성공해야 다른 요청이 거부됐을 때 그 이유를 해석할 수 있습니다.

예를 들어 정상 점주의 환불도 실패하는 상태에서 다른 점주의 환불 요청이 실패했다면, 소유권 검사가 제대로 작동했다고 말하기 어렵습니다. 기능 자체가 막힌 것인지, 의도한 인가 규칙이 요청을 거부한 것인지 구분해야 합니다.

이를 위해 가맹점 A와 B, 각 가맹점의 점주 계정, 메뉴, 주문, 결제를 더미 데이터로 준비하기로 했습니다. 테스트에서는 미리 알고 있는 이 객체들만 사용하고, 식별자를 대량으로 추측하지 않습니다.

| 확인할 질문 | 기대하는 결과 |
| --- | --- |
| A의 정상 주문·결제·환불이 가능한가? | 주문, 결제, 모의 원장의 상태가 일치합니다. |
| A가 B의 주문이나 메뉴를 바꿀 수 있는가? | 요청이 거부되고 B의 데이터는 그대로입니다. |
| 주문과 결제의 연결이 맞지 않는 요청은 어떻게 처리되는가? | 요청이 거부되고 어느 쪽에도 환불 효과가 발생하지 않습니다. |
| 동일한 승인·환불 요청을 다시 보내면 어떻게 되는가? | 처리 효과가 한 번만 발생합니다. |
| 승인 근거가 없는 요청으로 결제가 완료될 수 있는가? | 상태가 바뀌지 않고 후속 승인 호출도 발생하지 않습니다. |

여기서 합격 기준은 HTTP 상태 코드 하나가 아닙니다. 화면에서 오류가 보여도 내부에서 환불 호출이 발생했다면 안전하게 거부된 것이 아닙니다. 응답과 함께 DB 상태, 후속 호출 횟수, 더미 금액의 변화를 확인해야 합니다.

## ARTEX와 로컬 LLM에 맡길 역할

점검 도구로는 [ARTEX](https://github.com/namsh1125/ARTEX)를 활용하고, 모델은 Ollama를 통해 로컬에서 실행하는 방향으로 준비하고 있습니다. `qwen3:8b`는 사용할 모델 후보입니다. 이 글에서는 해당 모델의 테스트 정확도나 처리 속도를 측정한 결과를 다루지 않습니다.

로컬 모델을 고려한 이유는 점검 과정에서 사용하는 코드와 테스트 자료를 외부 모델 API로 보내는 경로를 줄이기 위해서입니다. 다만 로컬 추론을 사용한다고 해서 도구의 네트워크 호출이나 로그까지 자동으로 통제되는 것은 아닙니다. 모델 설정과 별개로 실행 도구의 접근 범위를 제한해야 합니다.

ARTEX에는 전체 네트워크를 자유롭게 탐색하도록 맡기기보다, 한 번에 하나의 질문을 주려고 합니다. 대상 주소와 포트, 사용할 더미 계정, 허용한 동작, 요청 상한, 중단 조건을 함께 지정하는 방식입니다. 실제 트래픽 제한은 프롬프트만 믿지 않고 프록시와 실행 환경에서도 강제할 계획입니다.

모델이 제시한 설명은 가설로 취급합니다. 최종 판정은 재현 가능한 요청과 서버 상태를 근거로 내립니다. 예상하지 않은 데이터 변경이나 범위 밖 연결이 관찰되면 자동 진행을 멈추고 원인을 확인하도록 기준을 정했습니다.

## 결과보다 먼저 증거를 남기는 방법을 정했습니다

문제를 발견한 뒤에야 로그를 켜면 수정 전 상태를 놓칠 수 있습니다. 그래서 실행 전후 자료를 어떤 단위로 남길지 먼저 정리했습니다.

브라우저 탐색에는 [Playwright MCP](https://github.com/microsoft/playwright-mcp)를 검토하고 있습니다. 화면에서 재현 절차를 확인한 뒤에는 Playwright Test 코드로 고정해 같은 조건으로 다시 실행하려고 합니다. MCP를 ARTEX에서 직접 호출할 수 있는지는 실제 연결 구성을 확인해야 하며, 필요하면 별도 실행기로 운영할 수 있습니다.

스크린샷은 실행 전, 실행 직후, 다시 조회한 최종 상태를 남기는 방식으로 계획했습니다. 점주 A와 B는 서로 다른 브라우저 컨텍스트를 사용하고, 개인 브라우저의 로그인 세션은 가져오지 않습니다.

여기에 Playwright trace를 함께 보관하면 동작 순서와 DOM, 네트워크 요청을 검토할 수 있습니다. 다만 trace는 화면 캡처보다 많은 정보를 포함하므로 그대로 공개할 자료로 보지 않습니다. [Playwright Trace Viewer 문서](https://playwright.dev/docs/trace-viewer)를 기준으로 로컬에서 확인할 예정입니다.

서버 쪽에서는 실행 ID, 테스트 사례 ID, 요청 ID를 연결해 다음 자료를 묶으려고 합니다.

- 프록시와 애플리케이션의 요청·응답 및 인가 결과
- 대상 주문·결제의 실행 전후 상태
- 카드·은행 모의 서버의 호출 횟수와 처리 결과
- 테스트 코드, 도구 버전, 배포 커밋과 데이터 시드

전체 DB를 덤프하기보다는 해당 사례의 객체만 제한해서 확인할 계획입니다. 로그에는 인증 헤더, 쿠키, 비밀번호를 남기지 않도록 하고, 원본 증거와 블로그 공개용 사본을 분리합니다. 스크린샷의 값을 가렸다고 해서 trace나 네트워크 기록에 남은 토큰까지 지워지는 것은 아니기 때문입니다.

현재는 수집 방식을 설계한 단계입니다. 이 글에 실제 테스트 결과를 대신하는 로그나 스크린샷을 넣지는 않았습니다.

## 수정 완료의 기준도 미리 정했습니다

취약점이 재현되면 최소 요청으로 발생 조건을 정리하고, 원인을 수정한 뒤 같은 데이터와 요청으로 다시 확인하려고 합니다. 수정 전에는 문제가 발생하고 수정 후에는 차단되는지 비교하되, 정상 기능이 계속 동작하는지도 함께 확인합니다.

예를 들어 다른 가맹점의 결제를 환불하려는 요청이 거부됐다는 사실만으로 검증을 끝내지 않습니다. 대상 결제와 잔액이 바뀌지 않았고, 후속 환불 호출도 없었으며, 본인 가맹점의 정상 환불은 성공해야 합니다. 이 조건을 자동 테스트로 남겨야 이후 변경에서도 같은 규칙을 확인할 수 있습니다.

지금까지 한 일은 코드의 인증 경계를 살펴보고 테스트 범위, 판정 기준, 증거 수집 방식을 정리한 것입니다. Windows 배포, 서비스 간 정상 연동, ARTEX의 실제 실행, 취약점 재현과 수정은 아직 검증하지 않았습니다.

환경 준비가 늦어지는 동안 테스트를 시작할 수는 없었지만, 무엇을 성공과 실패로 볼지는 먼저 정할 수 있었습니다. 이번 준비에서 가장 중요하게 생각한 부분도 그것입니다. 요청이 실패했다는 사실보다, 왜 실패했고 어떤 상태가 그대로 유지됐는지 설명할 수 있는 테스트를 만들려고 합니다.
