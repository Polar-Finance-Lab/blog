ARTEX를 처음 열면 대화, 작업, Agent, 발견 사항처럼 여러 메뉴가 보입니다. 무엇부터 누를지 막막하다면 **모델 선택 → 새 작업 → 세션 확인 → 추가 지시 → 결과 확인** 순서로 시작하면 됩니다.

이번 글에서는 더미 주문 응답 하나를 넣고, 어떤 정보를 입력하며 실행 과정과 결과를 어디서 확인하는지 살펴봅니다. Mac에서 실행한 한국어 ARTEX와 Ollama의 `qwen3:8b`를 사용했습니다. ARTEX 설치가 끝난 상태에서 시작하며, 실제 원큐오더 서버에 요청을 보내는 실습은 아닙니다.

## 1. ARTEX에 접속하고 사용할 모델을 선택합니다

브라우저에서 `http://127.0.0.1:8787`을 엽니다. 처음 설치했다면 관리자 설정을 먼저 마칩니다. 한국어 화면이 필요하면 [한국어 포크의 설치 안내](https://github.com/namsh1125/ARTEX)를 참고하면 됩니다.

왼쪽 **LLM** 메뉴를 누르면 등록된 모델 설정이 카드로 표시됩니다. 사용할 카드에 **활성화됨**이 표시되어 있는지 확인합니다. 이번 실습에서는 `ollama-qwen3-8b`를 사용했습니다.

<Image src={models} alt="ARTEX LLM 메뉴에서 qwen3:8b 설정이 활성화된 화면" sizes="(max-width: 768px) 100vw, 900px" style={{width:'100%',height:'auto'}} />

새 설정이 필요하면 **새로 만들기**를 누릅니다. 같은 Mac에서 실행 중인 Ollama에 연결하는 기본 입력은 다음과 같습니다.

| 항목 | 입력 예시 |
| --- | --- |
| 이름 | `ollama-qwen3-8b` |
| 형식 | `OpenAI (Chat Completions)` |
| 모델 | `qwen3:8b` |
| Base URL | `http://127.0.0.1:11434/v1` |
| API 키 | 로컬 Ollama용 입력값 `ollama` |
| 스트리밍 출력 | 이번 실습에서는 끄기 |

입력한 뒤 **저장**하고 해당 설정을 활성화합니다. 모델은 미리 Ollama에 내려받아 두어야 합니다. 이미 설정되어 있다면 새로 만들지 않고 기존 카드를 사용하면 됩니다.

작업마다 다른 모델을 쓰고 싶다면 새 작업 창의 **LLM 설정 체인**에서 선택합니다. 비워 두면 기본 설정을 사용합니다. 처음에는 모델 하나만 선택해 시작하는 편이 조작 순서를 익히기 쉽습니다.

## 2. 첫 실습에 넣을 자료를 준비합니다

처음부터 전체 서비스를 대상으로 지정하기보다 질문 하나를 정합니다. 이번 질문은 다음과 같습니다.

> 점주 A가 자기 매장이 아닌 다른 매장의 주문 응답을 받았다면, 무엇을 확인하고 어떻게 수정해야 할까요?

예제 데이터는 아래와 같습니다. 실제 서버 응답이 아니라 직접 만든 학습용 자료입니다.

```text
요청자: 로그인한 점주 A (merchantId=101)
요청: GET /demo/orders/2002
응답: HTTP 200
```

```json
{
  "orderId": 2002,
  "merchantId": 202,
  "totalAmount": 15000,
  "status": "PAID"
}
```

서비스의 규칙은 **점주는 자기 매장의 주문만 조회할 수 있다**입니다. 이 규칙을 함께 줘야 모델이 단순히 숫자가 다르다는 사실을 설명하는 데 그치지 않고, 허용된 동작과 실제 응답을 비교할 수 있습니다.

## 3. 새 작업의 이름·설명·목표를 입력합니다

왼쪽 **작업 → 새 작업**을 누릅니다. 처음에는 이름, 설명, 목표에 집중하면 됩니다. 작업 분류, 연결된 작업, 기업 자산 연결은 이 예제에서는 비워 둡니다.

### 이름: 나중에 찾을 수 있게 씁니다

```text
첫 실습 — 더미 주문 응답의 권한 검토
```

이름에는 대상과 확인할 내용을 함께 넣습니다. `테스트1`보다 `주문 조회 권한 검토`처럼 적으면 작업이 많아져도 찾기 쉽습니다.

### 설명: 대상과 자료, 허용 범위를 적습니다

아래 내용을 복사해 입력할 수 있습니다.

```text
블로그용 오프라인 분석 실습입니다. 실제 서버는 없습니다.
외부 접속, 명령 실행, 파일 읽기·쓰기, 웹 검색을 하지 마세요.
아래 더미 HTTP 응답만 분석하세요.

요청자: 로그인한 점주 A (merchantId=101)
요청: GET /demo/orders/2002
응답: HTTP 200
{"orderId":2002,"merchantId":202,"totalAmount":15000,"status":"PAID"}

규칙: 점주는 자신의 merchantId에 속한 주문만 조회할 수 있습니다.
점주 A가 다른 점주의 주문을 조회한 상황을 가정한 학습용 자료입니다.
```

설명에는 “보안 점검해줘”만 쓰지 않고 **무엇을 대상으로, 어떤 자료를 사용하며, 어디까지 허용하는지**를 적습니다. 실제 서비스 점검이라면 소유한 테스트 서버의 주소와 포트, 더미 계정의 역할도 이 위치에 추가합니다.

### 목표: 받고 싶은 결과를 구체적으로 적습니다

```text
제공된 더미 응답의 인가 문제를 분석해 한국어로 보고하세요.
1) 문제
2) 근거
3) 서버 측 수정 방법
4) 수정 후 재검증 2건
을 정리하세요.

제공 자료만으로 분석을 완료하고 추가 탐색은 하지 마세요.
실제 취약점을 재현했다고 표현하지 마세요.
```

설명이 작업의 재료라면 목표는 결과물의 형태입니다. “문제를 찾아줘”보다 위처럼 항목을 지정하면 결과를 읽고 비교하기 쉽습니다.

## 4. 실행 옵션을 확인하고 생성합니다

**고급 설정**을 펼치면 시간 제한과 첫 의도 전달 등의 옵션이 나옵니다. 이번 입력에서는 다음과 같이 설정했습니다.

| 항목 | 이번 입력 |
| --- | --- |
| 작업 시간 제한 | 10분 |
| 첫 의도 직접 전달 | 켜기 |
| 자산 커버리지 기능 | 끄기 — 오프라인 자료 분석이므로 사용하지 않음 |

**생성**을 누르면 목록에 작업이 추가됩니다. 별도의 실행 버튼을 다시 누르는 방식이 아니라 작업 생성 후 준비 과정이 시작됩니다. 목록의 작업 이름을 눌러 상세 화면으로 이동합니다.

이 실습에서는 외부 요청과 파일·명령 실행 도구를 제한하는 별도 보호 규칙도 적용했습니다. 설명에 금지 사항을 적는 것만으로 도구 실행이 강제로 막히는 것은 아닙니다. 실제 대상을 연결할 때는 **차단 규칙**, **작업별 자산 차단·허용**, 네트워크 접근 제한을 함께 준비합니다.

## 5. 세션에서 지금 무엇을 하는지 확인합니다

작업 상세에서 먼저 볼 곳은 **세션** 탭입니다. 왼쪽의 세션 목록을 선택하면 오른쪽에 해당 실행 내용이 나타납니다.

| 세션 | 확인할 내용 |
| --- | --- |
| 주 Agent | 작업에 추가 질문이나 지시를 보내는 곳 |
| 계획 Planner · 상황 분석 | 입력한 목표를 어떻게 나눴는지, 어떤 작업을 계획했는지 |
| Workers | 배정된 분석의 진행 과정과 결과 |
| 시스템 이벤트 · LLM 장애 조치 | 모델 호출이나 실행 관련 시스템 이벤트 |

작업을 열자마자 주 Agent 화면에 대화가 없다고 나오더라도 다른 세션에서는 준비가 진행 중일 수 있습니다. **계획 Planner**와 **Workers**를 각각 눌러 확인합니다.

이번 작업에서는 Planner가 주문의 `merchantId`를 비교하는 목표와 외부 접속 금지 제약을 등록하는 과정을 확인했습니다. 실행 내용을 볼 때는 출력량보다 **내가 준 범위 안에서 진행되는지**를 먼저 확인합니다.

## 6. 방향을 좁히려면 주 Agent에 추가 지시를 보냅니다

상세 화면의 **세션 → 주 Agent**를 선택하면 아래쪽 입력창으로 메시지를 보낼 수 있습니다. 새 작업을 만들 필요 없이, 현재 작업 안에서 원하는 결과를 더 구체적으로 요청하는 방식입니다.

이번 실행에서는 Planner가 목표 등록을 반복해 작업을 **일시 중지**했습니다. 그 상태에서 주 Agent에 아래처럼 자료 분석만 요청했고, 약 2분 15초 뒤 답변을 받았습니다. 자동 점검 전체를 완료한 것이 아니라, 작업 안에서 추가 질문을 보내고 답변을 확인한 실습입니다.

```text
이 작업은 오프라인 사용법 실습입니다.
작업을 재개하거나 도구를 호출하지 마세요.
다음 더미 사례만 한국어로 답하세요.
점주 A의 merchantId는 101인데 주문 조회 응답은 HTTP 200이며
{orderId:2002,merchantId:202,totalAmount:15000,status:PAID}입니다.
규칙은 자기 매장 주문만 조회 가능입니다.
문제, 근거, 서버 수정 방법, 재검증 2건을 총 10문장 이내로 정리하세요.
실제 서버 취약점이 아닌 제공 자료 분석임을 명시하세요.
```

결과가 너무 길면 “표로 정리해줘”, 근거가 부족하면 “입력 자료의 어떤 필드가 근거인지 적어줘”처럼 요청을 좁힙니다. 새로운 서비스 주소나 계정을 추가하는 지시는 작업 범위를 바꾸므로 별도로 검토합니다.

답변은 다른 매장의 주문이 반환된 문제와 정상·거부 테스트를 구분했습니다. 다만 그대로 수정 지침으로 옮기기 전에 두 부분을 바로잡아야 합니다.

- 비교할 것은 요청에서 임의로 보낸 `merchantId`가 아니라 **인증된 사용자의 매장과 조회한 주문의 소유 매장**입니다.
- 로그인된 A가 B의 주문을 요청하는 사례는 인증 실패가 아닌 권한 문제입니다. 답변의 `401`을 그대로 기대값으로 쓰지 않고, 서비스 정책에 맞는 `403` 또는 존재 여부를 숨기는 `404`와 **주문 정보가 응답에 없는지**를 확인합니다.

또한 이 응답만으로 서버 코드에 어떤 검사가 빠졌는지까지 확정할 수는 없습니다. 모델의 답변은 검토 초안으로 사용하고, 실제 구현과 테스트로 확인할 항목을 나누면 됩니다.

## 7. 결과는 세션·발견 사항·보고서를 나눠 봅니다

**세션**은 실행 과정을 읽는 곳이고, **발견 사항**은 등록된 항목을 모아 보는 곳입니다. **보고서** 탭에서는 정리된 Markdown을 확인하고 **복사** 버튼으로 가져올 수 있습니다. **재검증**은 발견한 문제를 수정한 뒤 다시 확인하는 작업에 사용합니다.

이번 실습에서는 주 Agent의 답변은 세션에 남았지만 보고서의 **확인된 발견 사항은 0개**였습니다. 대화로 분석 답변을 받는 것과 발견 사항이 등록되는 것은 별개입니다. 보고서에 “확인된 취약점이 없습니다”라고 표시되어도, 중지된 작업을 안전성 검증 완료로 해석하면 안 됩니다.

여기서 중요한 것은 화면에 결과가 있다는 사실보다, 입력한 질문에 답하고 있는지입니다. 이번 예제의 답변을 검토할 때는 아래 기준을 사용합니다. 이는 답변을 평가하기 위한 기준이지 실제 서버에서 취약점이 확인됐다는 뜻은 아닙니다.

| 확인 항목 | 예제에서 찾아야 할 내용 |
| --- | --- |
| 문제 | 다른 매장의 주문을 조회할 수 있는 객체 단위 인가 문제 |
| 근거 | 요청자 `merchantId=101`, 응답 주문 `merchantId=202`, 상태 `HTTP 200` |
| 수정 방향 | 로그인한 점주의 매장과 주문의 소유 매장을 서버에서 대조 |
| 정상 재검증 | A가 A의 주문을 조회하면 성공 |
| 거부 재검증 | A가 B의 주문을 조회하면 주문 정보가 반환되지 않음 |

모델이 새로운 URL이나 코드 위치를 덧붙였을 때는 원래 자료에 있었는지 확인합니다. 자료에 없는 내용을 재현 근거로 가져오면 안 됩니다.

## 8. 멈추거나 이어서 진행하는 방법

작업 전체를 멈추려면 상세 화면 위의 **일시 중지**를 누릅니다. 다시 진행할 때는 중지 후 표시되는 재개 버튼을 사용합니다. 일시 중지는 기록을 삭제하는 동작이 아니므로 이전 세션을 읽으면서 범위를 다시 정리할 수 있습니다.

일반 **대화** 화면에서 한 번의 답변만 멈추려면 **이번 실행 중지**를 사용합니다. 작업 전체를 제어하는 버튼과 구분해서 사용합니다.

이번처럼 결과가 필요 이상으로 넓어지면 무작정 기다리기보다, 기록을 확인하고 작업을 멈춘 뒤 원하는 질문과 출력 형식을 좁혀주는 편이 좋습니다.

## 처음 사용할 때 기억할 순서

1. **LLM**에서 사용할 모델을 선택합니다.
2. **작업 → 새 작업**에서 설명과 목표를 구분해 입력합니다.
3. **생성** 후 작업 이름을 눌러 상세 화면으로 이동합니다.
4. **세션**에서 Planner와 Worker의 진행을 확인합니다.
5. **주 Agent**에 추가 지시를 보내 결과를 구체화합니다.
6. **발견 사항·보고서**에서 결과를 확인하고 근거를 검토합니다.

처음부터 모든 메뉴를 익힐 필요는 없습니다. 하나의 작은 질문을 넣고, 그 질문이 실행 과정과 결과에 어떻게 이어지는지 따라가면 ARTEX의 기본 조작 흐름을 이해할 수 있습니다.
