원큐오더의 Windows 테스트 환경을 기다리는 동안, Mac에 준비한 ARTEX부터 직접 열어봤습니다. 어떤 메뉴에서 모델을 연결하고 작업의 범위를 입력하는지 익히는 것이 이번 사용의 목적입니다.

이 글은 설치 완료 상태에서 시작하는 짧은 사용기입니다. 실제 서비스를 대상으로 침투 테스트를 실행한 기록은 아닙니다. 아래 이미지는 원본 프로젝트의 소개 이미지를 가져온 것이 아니라, 로컬 ARTEX 화면을 직접 조작하면서 촬영한 스크린샷입니다. 영상 녹화는 포함하지 않았습니다.

## 이번에 사용한 환경

| 항목 | 확인한 환경 |
| --- | --- |
| Mac | Apple M4, 메모리 32 GiB |
| ARTEX | 한국어 포크 `namsh1125/ARTEX`, 커밋 `0846008`, UI 표시 `dev` |
| ARTEX 접속 주소 | `http://127.0.0.1:8787` |
| Ollama | `0.32.13` |
| 모델 | `qwen3:8b` |
| 모델 연결 방식 | 로컬 Ollama의 OpenAI 호환 엔드포인트 |

이 환경은 성능 권장 사양을 측정한 결과가 아닙니다. 특히 모델 파일을 내려받았다는 사실과 ARTEX에서 긴 작업을 끝까지 수행할 수 있다는 사실은 구분해야 합니다.

한국어 화면을 사용하려면 설치 경로에도 주의해야 합니다. 이 포크의 [README](https://github.com/namsh1125/ARTEX/tree/0846008)는 한국어 화면에 소스 빌드를 사용하도록 안내합니다. 원본 Docker 이미지나 원본 릴리스를 실행하면 이 글과 메뉴 언어가 다를 수 있습니다.

## 1. 접속하면 작업 목록부터 확인합니다

로컬 주소에 접속하면 왼쪽에 기능 메뉴와 시스템 메뉴가 표시됩니다. 이번 환경에는 기존 작업이 없었고, 오른쪽 위에 **새 작업** 버튼이 보였습니다.

<Image src={tasks} alt="로컬 ARTEX의 비어 있는 작업 목록과 새 작업 버튼" sizes="(max-width: 768px) 100vw, 900px" style={{width:'100%',height:'auto'}} />

처음에는 세 메뉴를 구분하면 편합니다.

- **LLM**: 사용할 모델과 연결 주소를 설정합니다.
- **대화**: 플랫폼 운영 도우미와 대화하는 화면입니다. 일반 채팅처럼 보여도 도구를 다루는 Agent라는 점을 확인해야 합니다.
- **작업**: 점검 대상과 목표, 작업별 범위와 실행 옵션을 입력합니다.

모델 연결을 확인하지 않은 채 작업을 만들면, 작업 자체의 문제인지 모델 호출 문제인지 구분하기 어려워집니다. 그래서 먼저 LLM 화면으로 이동했습니다.

## 2. LLM 카드에서 Ollama 연결 정보를 확인합니다

왼쪽 **LLM** 메뉴를 누르고 활성 설정 카드를 클릭하면 편집 패널이 열립니다. 이번에는 이미 준비된 `ollama-qwen3-8b` 설정을 열어 확인했으며, 값을 변경해 저장하지는 않았습니다.

<Image src={settings} alt="qwen3:8b 모델과 로컬 Ollama Base URL을 보여주는 ARTEX LLM 편집 패널" sizes="(max-width: 768px) 100vw, 900px" style={{width:'100%',height:'auto'}} />

확인한 핵심 항목은 다음과 같습니다.

| 화면 항목 | 이번 설정 |
| --- | --- |
| 형식 | OpenAI (Chat Completions) |
| 모델 | `qwen3:8b` |
| Base URL | `http://127.0.0.1:11434/v1` |
| 스트리밍 출력 | 켜짐 |

여기서 `OpenAI`는 선택한 API 형식입니다. 이번 설정의 요청 목적지는 OpenAI 클라우드가 아니라 Base URL에 지정한 로컬 Ollama입니다. ARTEX와 Ollama를 같은 Mac에서 네이티브로 실행하는 조건의 주소이므로, 컨테이너 안에서 ARTEX를 실행한다면 `127.0.0.1`이 가리키는 대상부터 다시 확인해야 합니다.

API 키 입력란은 기존 값이 설정됐다는 표시만 보였습니다. 키를 펼치거나 새로 입력하지 않았습니다. 자신의 환경을 캡처할 때도 키 원문이 보이지 않는지 확인하는 편이 좋습니다.

### 화면의 컨텍스트 값과 실제 모델의 컨텍스트는 다릅니다

편집 패널에는 컨텍스트 창이 `40`K로 설정되어 있었습니다. 하지만 터미널에서 `ollama ps`를 확인했을 때 실행 중인 모델의 `CONTEXT`는 `32768`이었습니다. 같은 출력에서 모델은 `100% GPU`, `SIZE`는 `10 GB`로 표시됐습니다. 이는 그 시점의 Ollama 출력이지 전체 시스템 메모리 사용량이나 성능 벤치마크가 아닙니다.

ARTEX 화면 설명에 따르면 이 컨텍스트 설정은 로컬 압축 임계값 계산에 사용됩니다. 값을 높인다고 Ollama의 실제 컨텍스트가 함께 늘어나는 것은 아닙니다. 따라서 스크린샷의 40K를 권장값으로 복사하기보다, 모델 서버의 실제 설정과 일치시키는 작업이 먼저입니다. 이번 사용기에서는 값을 수정하지 않고 차이를 기록했습니다.

또한 초당·분당 요청 제한의 `0`은 요청 금지가 아니라 **제한 없음**입니다. 이것은 LLM 요청 제한이며, 점검 대상 서버로 보내는 HTTP 요청 속도를 제한하는 설정과도 구분해야 합니다.

## 3. 연결 테스트와 실제 응답을 구분합니다

편집 패널 아래 **연결 테스트**를 눌러봤습니다. 버튼은 `테스트 중…`으로 바뀌었다가 다시 돌아왔습니다. 다만 이번 촬영에서는 완료 알림의 성공·실패 결과와 응답 내용을 확보하지 못했습니다. 따라서 카드의 `정상` 표시나 버튼 복귀만으로 이번 호출의 성공을 판정하지 않았습니다.

실제로 사용할 때는 완료 알림의 결과와 응답 내용을 함께 확인해야 합니다. 이 버튼의 성공이 확인되더라도 도구 호출, 긴 대화, 작업의 끝까지 정상 동작한다는 보장은 아닙니다.

## 4. 짧은 대화를 보내고 중단 기록을 확인했습니다

**대화** 메뉴에서는 `Auto`가 기본 Agent로 표시됐습니다. 다음처럼 도구를 사용하지 않는 연결 확인용 메시지를 보냈습니다.

```text
/no_think
이 메시지는 로컬 모델 연결 확인용입니다. 도구 호출, 명령 실행,
파일 접근, 네트워크 요청, 작업 생성 없이 다음 문장만 답해주세요:
로컬 연결 확인 완료.
```

이번에는 최종 답변이 나오기 전에 **이번 실행 중지**를 눌렀습니다. 중단 후 화면에는 실행 경과 `59.8s`, 최종 상태 `aborted_streaming`, 하위 오류 `context canceled`가 표시됐습니다. 또한 도구 호출 전에 종료됐다는 안내를 확인했습니다.

<Image src={stopped} alt="최종 답변을 받기 전에 중지한 ARTEX 대화와 59.8초 실행·도구 호출 전 종료 안내" sizes="(max-width: 768px) 100vw, 900px" style={{width:'100%',height:'auto'}} />

`context canceled`는 이번에는 제가 중지 버튼을 누른 뒤 나온 결과입니다. 이것만으로 모델이나 네트워크의 장애라고 판단하지 않았습니다. 반대로 모델이 Ollama에 올라와 있다는 사실만으로 대화가 성공했다고 판단할 수도 없습니다.

이 59.8초는 응답 지연 벤치마크가 아니라 중단 시점까지의 실행 경과입니다. 모델의 초기 로딩, 입력 처리, ARTEX의 요청 구성 중 어디에서 시간이 걸렸는지는 아직 분리해서 측정하지 않았습니다. `/no_think`를 입력했다는 사실만으로 실제 추론 모드가 꺼졌다고 단정하지도 않았습니다.

## 5. 새 작업에서는 설명과 목표를 나눠 입력합니다

**작업 → 새 작업**을 누르면 이름, 설명, 목표를 입력하는 창이 열립니다. 사용법을 확인하기 위해 다음처럼 입력했습니다.

- **이름**: 나중에 목록에서 구분할 수 있는 작업명
- **설명**: 대상 환경, 허가된 범위, 더미 데이터 여부와 금지 사항
- **목표**: 어떤 상태를 확인하고 무엇을 근거로 판정할지

<Image src={draft} alt="실행하지 않는 설명용 초안임을 명시한 ARTEX 새 작업 입력 화면" sizes="(max-width: 768px) 100vw, 900px" style={{width:'100%',height:'auto'}} />

화면에는 작업별 자산 차단·허용 규칙과 LLM 설정 체인도 있었습니다. 안내에 따르면 차단 규칙이 우선 적용되고, 작업별 허용 규칙이 없다면 허용 목록을 적용하지 않습니다. 범위 설명을 문장으로 적는 것과 실행 경계를 강제하는 것은 다르므로, 실제 점검에서는 네트워크 제한도 함께 준비해야 합니다.

고급 설정을 펼치면 작업 시간 제한, planner 하트비트, 첫 의도 직접 전달 등의 옵션이 나옵니다. 시간 제한은 즉시 강제 종료가 아니라 결과 기록과 최종 판단을 포함한 정상 종료 절차를 시작하는 것으로 설명되어 있습니다. 긴급 중단 수단과 같다고 생각하면 안 됩니다.

이번에는 Windows 환경과 실제 대상 주소가 확정되지 않았으므로 **생성 버튼을 누르지 않았습니다.** 입력 화면을 촬영한 뒤 취소했습니다. 이 이미지는 실행 결과가 아니라 입력 예시입니다.

## 기록 메뉴에서 확인할 것

왼쪽에는 **LLM 기록**, **도구 실행**, **트래픽**, **발견 사항**이 나뉘어 있습니다. 모델의 설명만 읽기보다, 실제 실행이 있었는지와 무엇을 근거로 결론을 내렸는지 함께 확인할 때 사용할 메뉴입니다.

이번에 처음 연 LLM 기록 화면에는 호출 기록이 0건으로 표시됐습니다. 연결 테스트 버튼을 눌렀다는 사실과 이 목록에 실행 기록이 남는다는 사실을 같은 것으로 취급하지 않았습니다. 실사용에서는 작업이나 대화를 실행한 뒤 해당 기록이 어떻게 연결되는지 확인해야 합니다.

## 이번에 확인한 범위

이번에는 로컬 화면 접속, LLM 설정 확인, 연결 테스트 버튼 조작, 짧은 대화 전송과 중지, 새 작업 입력과 취소까지 직접 수행했습니다. 설정을 바꾸거나 보안 점검 작업을 생성하지 않았고, 원큐오더 또는 외부 서비스에 대한 스캔도 실행하지 않았습니다. 대화 기록 1건은 중단 상태로 남겼습니다.

처음 사용하면서 가장 주의할 부분은 UI의 설정값과 실제 실행 상태를 구분하는 일이었습니다. 컨텍스트 40K라는 입력값, 카드의 정상 표시, 테스트 버튼의 복귀만으로 모델이나 작업 전체가 검증됐다고 볼 수는 없습니다. 실제 응답과 기록을 확인한 범위까지만 결과로 남기는 것이 이 도구를 익히는 출발점이라고 생각합니다.
